# HARDENING ROADMAP — خارطة تحصين النظام (مبنية على أعطال حقيقية 2026-09-22)

كل بند هنا مستند إلى عطل فعلي حصل، مش تخمين. الترتيب بحسب خطورة الأثر وتكلفة الإصلاح.

## الأعطال الحقيقية اللي حصلت النهاردة — والدروس

| العطل | الجذر | الدرس |
|---|---|---|
| انقطاع كل الردود | ترايال Railway خلص ون8ن+Postgres وقفوا | اعتماد على مزود سحابي واحد بلا إنذار مبكر ولا خطة استمرارية |
| ضياع ورن8ن القديم (وركفلو+كريدنشالز) | مفيش باك أب تلقائي — آخر تصدير يدوي 11 سبتمبر | باك أب مجدول آلي إجباري |
| عطل حجز حي 500 | `NameError: _dig` — كود مات مراجعته الاختبارات | اختبارات الرحلة كانت بتعدّي المسار بصدفة (قصور ذوات) |
| اختبار رحلة كان فاشل بصمت | فيكسچر بتاريخ ثابت قديم (قنبلة زمنية) | تشغيل الاختبارات يومياً آلياً يكشف التعفن الزمني |
| كل القنوات وقعت مرة تانية | مفتاح Postgres على IPv6-only | تحقق لايف من كل طرف اتصال بعد أي ترحيل |
| الترحيل شال إعدادات القطع | التصدير كان أقدم من قرار القطعة (config drift) | مصدر حقيقة واحد للحالة + تصدير مجدول |

## الدفعة 1 — قيد التنفيذ (هذه الجلسة)
1. **CI إجباري على ريبو النشر**: pytest على كل push + تشغيل يومي مجدول (يكشف القنابل الزمنية والتعفن). الاختبارات بوابة قبل أي نشر.
2. **مطاردة القنابل الزمنية**: أي تاريخ ثابت في الاختبارات يتبدل بنسبي.
3. **باك أب n8n مجدول**: سكريبت تصدير + snapshot فوري للحالة الحالية (بعد كل تعديلات اليوم) داخل الريبو الخاص.
4. **مطاردة أي دالة مستخدمة غير معرفة** في كل الوحدات (فحص استاتيكي سريع — نفس نوع عطل _dig).

## الدفعة 2 — متابعة (تحتاج قرار مالك)
1. **ويبهوك المزودين** (Gupshup/SuperChat/Thikaa): آخر خطوة لرجوع واتساب/إنستجرام/ماسنجر — من الكونسولات.
2. **تنبيه مبكر لانتهاء ترايالات Railway**: حاجة بسيطة — مراقبة usage + تنبيه قبل الانتهاء بأسبوع (أو تحويل لحساب مدفوع بدل الدوران على حسابات).
3. **تنبيه ترايال العيادة في منصة ميرونا نفسها** (20 سبتمبر) — قرار منتج.
4. **typing على واتساب**: أول ما المزود يدعم (Meta Cloud API يدعم ≤25 ثانية عبر mark-as-read).

## الدفعة 3 — الوكيل الأذكى بأدوات أوسع (تصميم قائم، تنفيذ على دفعات)
الأساس: `docs/agent_upgrade_design.md`. القواعد غير قابلة للنقاش: النموذج يقترح فقط، orchestrator+ledger ينفذون، كل قيمة في الرد تترجع لحقائق.
أدوات مقترحة تُضاف لحلقة الوكيل (كل واحدة = صف قرار + منفذ + اختبار رحلة):
1. **استعلام مواعيدي القادمة** (للمريض الحالي) — يلغي "مش فاكر حجزتي امتى".
2. **إلغاء/تعديل حجز موجود برقم الحجز** — مسار c1 موجود للتنفيذ، ينقصه عرض الحجوزات.
3. **مواعيد العمل والعنوان والفروع** — أدوات قراءة من DB بدل اجابات النموذج العامة.
4. **متابعة الخدمة والسعر** (خدمات العيادة كأداة استعلام مهيكلة بدل FAQ حر).
5. لاحقاً: **handoff ذكي** برفع أولوية تلقائي عند تكرار فشل الفهم (موجود جزئياً — تعميقه).

## الدفعة 4 — مرونة تشغيلية
1. فحص `/health` يشمل فحص DB (مش مجرد نبضة عملية).
2. restartPolicy على n8n + تأخير إقلاع ينتظر جاهزية الـ DB.
3. مسار DB بديل للطوارئ (pooler session ↔ transaction) موثق ومختبر.
4. مراقبة `platform_hala_alerts` يوصلها إشعار فعلي (تلغرام للمالك).

## قواعد ثابتة تُراجع مع كل دفعة
- كل إصلاح معاه اختبار انحدار في نفس الكوميت.
- الاختبارات تُشغَّل يومياً آلياً — التعفن الزمني بيتكشف خلال 24 ساعة مش بعد شهر.
- لا نشر بدون بوابة CI خضرا.
- كل قيمة في رد المريض تترجع لحقائق — مفيش استثناءات.
