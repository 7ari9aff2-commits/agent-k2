# AGENT TOOLS PLAN — خطة الوكيل الذكي بالأدوات (تصميم قبل تنفيذ — 2026-09-23)

خطة الدفعة 3 من `HARDENING_ROADMAP.md`. مبنية على الكود الفعلي وأرقام حقيقية من `ai_requests`
(آخر 7 أيام). الهدف: أوسع قدرة للوكيل بأقل خطأ وأقل تكلفة، مع خفض الخطر لا زيادته.

## 1. الجرد الفعلي — إيه اللي موجود أصلاً (مفاجأة سارة)

الأدوات القرائية الأربعة **موجودة وموصولة** في حلقة الوكيل (`app/services/dialogue.py`):

| الأداة | المصدر | الحالة |
|---|---|---|
| `Check_Doctor_Availability` | sub-workflow التوفر (deterministic) | شغالة (رحلة الحجز كلها عليها) |
| `Search_Clinic_FAQ` | knowledge_base معزولة بالعيادة | شغالة — والـ prefetch الثقيل اتشال (P1.2 منفذ) |
| `Get_Clinic_Services_And_Doctors` | كتالوج العيادة | شغالة |
| `Get_My_Appointments` | حجوزات المريض الحالي فقط | شغالة |

جهة التعديلات **مبنية بالكامل**: `cancel_appointment` و `reschedule_appointment` ليهم صفوف قرار
في orchestrator (سطر 771+)، منفذين حتميين (`execute_cancel`/`execute_reschedule`)، دفتر عمليات،
وتأكيد قبل التنفيذ. يعني "إلغاء حجزي" و"عدّل حجزي" ماشيين بالفعل عبر المسار الآمن.

**الاستنتاج المهم:** المشكلة ليست نقص أدوات — المشكلة هي فجوات جودة وتشغيل حولها.
ده يغيّر شكل الخطة: أقل كود جديد، وأكثر تحقق.

## 2. الفجوات الحقيقية (بالأدلة) — أولويات الخطة

### أ. التحقق الحي لكل نية (أهم بند)
تصميم P3 نفسه يقول: "لم يُختبر ضد الـ LLM الحي لكل نية". اليوم اتحقق فعلياً من:
تحية ✓، حجز ✓ (بعد إصلاح _dig)، سؤال أسعار/خدمات (غير مختبر)، إلغاء (غير مختبر حي)، تعديل (غير مختبر حي)، FAQ (غير مختبر حي).
**التنفيذ:** سيناريو موقّع لكل نية على الإنتاج (نفس أسلوب فحوصات اليوم) + تصوير النتيجة. عتبة القبول: 200 + رد مؤرَّخ بمصدره لكل نية.

### ب. أداة واحدة ناقصة فعلاً: `Get_Clinic_Info`
مواعيد العمل والعنوان والفروع — سؤال يتكرر كثيراً، ودخول نتيجة الـ FAQ فيه غير مضمون لأنه يعتمد
على وجود مقال في knowledge_base. أداة قراءة من `clinic_business_hours` + `branches`.
- **المميزات:** أرقام دقيقة من DB، صفر اختلاق، يقلل handoff.
- **العيادات/الأضرار:** أداة إضافية في البرومبت (~150 توكن تعريف) + نداء SQL عند الاستخدام فقط؛ خطر التضخم لو أضفنا أدوات كثيرة (قاعدة: لا نتجاوز 6 أدوات — فوقها جودة الاختيار بتتدهور).
- **الفشل المحتمل:** عيادة من غير ساعات مسجلة → الأداة ترجع فراغ → الكومبوزر ممنوع يدّعي — الفشل يتحول لسؤال توضيح آمن (fail-closed موجود أصلاً).

### ج. إغلاق الديون المعلنة في P3 (جودة)
1. `grounding.py` يتيم من أيام الأيام — قرار: حذف آمن (البديل الأقوى موجود: عقد الأدلة في الكومبوزر).
2. `call_primary_model` (النسخة الميتة قبل الأدوات) — حذف.
3. فرع `if_single_agent_result_phase` الميت — حذف أو توصيل.
4. حذف `LLM_TEMPERATURE` الميت من الإعدادات.
(كلها تنظيف يقلل سطح الأخطاء — كود ميت = مساحة للباجات المستقبلية.)

### د. Cheap-turn short-circuit (P2.5 — لم يُنفذ)
قبل نداء الـ LLM: "أيوه/لأ" أثناء AWAIT_CONFIRMATION واختيار رقم سلوت — الجدول بيحلها بعد النداء
الغالي؛ نقلها قبل النداء = توفير نداء LLM كامل على نسبة كبيرة من تيرنات التأكيد.

## 3. التكلفة — أرقام حقيقية من ai_requests

المقاس على آخر 7 أيام (تيرن إنتاجي = نداء أساسي + كومبوزر):

| النموذج | نداءات | متوسط in | متوسط out | المجموع |
|---|---|---|---|---|
| deepseek-v4-flash (الإنتاج) | 16 | 3218 | 403 | 3622 |
| deepseek-v3.2 (سجل أقدم) | 26 | 2982 | 101 | 3083 |

- **التيرن الواحد ≈ 3.2–3.6 ألف توكن** + نداء الكومبوزر (~1–1.5 ألف). بأسعار فئة deepseek-flash
  (أقل من دولار لكل مليون توكن تقريباً — تراجع أسعار المزود وقت الفاتورة): **أقل من سنت واحد للتيرن**.
- **أثر الأدوات الجديدة على التكلفة ≈ صفر تقريباً**: الأداة القرائية = SQL رخيص + 200–400 توكن نتيجة
  داخل السياق. الحلقة مقيدة أصلاً (3 دورات/4 نداءات + كاش للنداءات المكررة).
- **المخفض الحقيقي غير منفذ**: (1) cheap-turn short-circuit — يمسح نداء الـ LLM كلياً في تيرنات
  التأكيد والاختيار (نسبة معتبرة من الترافيك الحقيقي)، (2) prompt caching للبرومبت الثابت (~3 آلاف
  توكن تيرن بعد تيرن) لو المزود يدعم — توثيق كفرصة مو كوعد.
- **سقف الحماية موجود**: بوابة التكلفة (cost gate) بتشتري مسودة الوكيل مباشرة وتتخطى الكومبوزر —
  التكلفة العليا مقفولة بالتصميم.

## 4. الجودة — ليه الأدوات مش هتزود الأخطاء

1. **أداة القراءة لا تغيّر أي حالة** — أخطر حاجة فيها إن ردها يوصل غير دقيق، والكومبوزر ملزم
   بعقد الأدلة: كل جملة تترجع لـ fact_id، و`tool_error` ممنوع يبني منها أي تأكيد (fail-closed).
2. **كل أداة جديدة = اختبار وحدة + سطر في رحلة الحجز + جرة حي واحدة لكل نية** — نفس بوابة CI اللي
   مسكت عطل `_dig` وقنبلة التاريخ.
3. **قاعدة العدد**: 6 أدوات كحد أقصى — بعد كده دقة اختيار الأداة بتنخفض (معروف من الـ LLM tool-use).
4. الأدوات الأربع الحالية استقرت لايف خلال أسوأ يوم تشغيلي (يوم الترحيل كله) — قاعدة صلبة نبني عليها.

## 5. الأمان — الثوابت غير القابلة للنقاش

1. **النموذج لا يملك أي أداة تعديل** — الإلغاء/التعديل/الحجز قرارات حتمية بعد تأكيد المريض
   عبر دفتر العمليات. الأدوات للنموذج قراءة فقط.
2. **عزل المريض مش من النموذج**: `Get_My_Appointments` يأخذ patient_id من سياق الخادم
   (state بعد التحقق الموقّع) مش من arguments النموذج — بند أمان يُراجع في كود التنفيذ
   ويُثبت باختبار (محاولة حقن patient_id لآخر → تتجاهل الأداة المعامل).
3. **عزل العيادة**: كل SQL مفحوص clinic_id (موجود بالتصميم ويُعاد التأكد في اختبار كل أداة).
4. **حقن النصوص العربي**: كل الاستعلامات parameterized — النص لا يدخل الـ SQL كأمر أبداً.
5. **التدقيق**: كل نداء LLM مسجل في ai_requests (موديل، توكن، زمن) وكل قرار في agent_audit_log —
   أي سلوك غريب قابل للتحليل بأثر رجعي.
6. **حدود الإساءة**: burst gate قائم + حد أدوات/دورات مقيد — مفيش طريق لأستهلاك مفتوح.

## 6. خطة التنفيذ — 4 دفعات صغيرة، كل واحدة ببوابة CI خضرا

| الدفعة | المحتوى | معيار القبول |
|---|---|---|
| B1 | التحقق الحي لكل نية (فحوصات موقعة على الإنتاج + توثيق النتائج) | 200 + رد مؤرَّخ لكل نية |
| B2 | أداة `Get_Clinic_Info` (ساعات/فروع/عنوان) + اختباراتها | جرة لايف + اختبار عزل |
| B3 | تنظيف الميت (grounding orphan، call_primary_model، الفرع الميت، LLM_TEMPERATURE) | نفس 101 اختبار خضرا بعد الحذف |
| B4 | cheap-turn short-circuit (توفير نداء الـ LLM في التأكيدات) | اختبار: تأكيد نعم/لا من غير نداء LLM + نتيجة مطابقة |

التراجع في أي لحظة: n8n باك أب موجود + دمج تدريجي — أي دفعة تتسحب بـ revert كوميت واحد.
